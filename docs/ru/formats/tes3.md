# Байтовая раскладка TES3 и константы ландшафта

Источник для всего ниже — исходники OpenMW, ветка `master`, прочитано 2026-09-18.
OpenMW — рабочая независимая реализация формата, поэтому его ридер/райтер надёжнее
любой вики.

---

## Кодировка строк: cp1252, и это жёстко

Все строки в плагине TES3 — **Windows-1252**. Кириллицы в них не бывает, и это касается
всего: автора, описания, ID записей, путей к мешам и текстурам, отображаемых имён.

Выяснилось на первом же прогоне: `Greatness7/tes3` отказывается записывать непредставимый
текст с `InvalidData` вместо того, чтобы молча испортить файл. Поведение правильное, и мы
закрепили его тестом (`tes3_out::plugin::tests::rejects_text_outside_cp1252`).

Следствие на потом: когда пойдёт настоящий контент, непредставимые символы надо будет
обрабатывать осознанно — транслитерацией или заменой, — а не надеяться, что их не встретится.

**Русские моды проходят байт в байт.** Переводы и для Oblivion, и для Morrowind пишут строки в
cp1251. Мы читаем их как cp1252 (`tes4_read::cp1252`) и пишем как cp1252 (`encoding_rs`
внутри `Greatness7/tes3`), а обе таблицы взаимно однозначны на всех 255 ненулевых байтах,
включая пять неопределённых в cp1252 (0x81, 0x8D, 0x8F, 0x90, 0x9D ↔ U+0081…U+009D). Значит
байты имени доходят до `FNAM` неизменными, и русский Morrowind покажет «Копьё драконоборца».
Закреплено тестом `transform::objects::tests::every_name_byte_survives_the_round_trip`
(2026-09-24). `esmtool` при этом показывает «Êîïüå…» — он читает те же байты как cp1252,
это не порча. **Не проверено в игре:** русской версии Morrowind у нас нет.

От Latin-1 cp1252 отличается только диапазоном 0x80..=0x9F, то есть таблицей из 32 символов;
всё остальное совпадает с кодовыми точками Unicode. Поэтому отдельная библиотека кодировок
не нужна — декодер лежит в `crates/tes4_read/src/cp1252.rs`.

## Контейнер

**Заголовок записи — 16 байт** (`components/esm3/esmwriter.cpp`, `startRecord`):

| Смещение | Размер | Поле |
|---|---|---|
| 0 | 4 | имя типа записи, ASCII (`LAND`, `CELL`, `STAT`…) |
| 4 | 4 | размер данных, u32 — **без** этих 16 байт |
| 8 | 4 | не используется, пишется нулём |
| 12 | 4 | флаги, u32 |

**Заголовок сабрекорда — 8 байт** (`startSubRecord`): имя (4 ASCII) + размер (u32).

Ключевые отличия от TES4/TES5, которые упрощают райтер:

- **нет дерева GRUP** — плоский поток записей
- **нет сжатия** записей (в TES4/TES5 записи бывают zlib-сжатыми)
- размер сабрекорда — u32 (в TES4/TES5 — u16, из-за чего там нужны `XXXX`-обходы)
- удаление — сабрекордом `DELE` (3 байта нулей), а не флагом в заголовке
- ссылки на объекты — **строковые ID**, а не FormID

## Константы ландшафта: TES3 против TES4/TES5

| | TES3 | TES4 / TES5 |
|---|---|---|
| Вершин на сторону | **65** (`LandRecordData::sLandSize`) | **33** (`ESM4::Land::sVertsPerSide`) |
| Размер ячейки, юнитов | **8192** (`Constants::CellSizeInUnits`) | **4096** (`ESM4::Land::sRealSize`) |
| Шаг вершины | **128 юнитов** | **128 юнитов** |
| `heightScale` | **8** | **8** |
| Кодирование высот | float-смещение + int8-дельты | float-смещение + int8-дельты |

Источники: `components/esm3/loadland.hpp`, `components/esm3/landrecorddata.hpp`,
`components/esm4/loadland.hpp`.

**Вывод: 2×2 ячейки TES4/TES5 = 1 ячейка TES3, вершина в вершину.** Шаг и схема
кодирования совпадают, значит слияние идёт без ресемплинга и без потери точности.
Референс `tes4skyrim` измерил это в обратную сторону («zero resampling error»,
`tes4_export/morrowind_land.py`: 65×65 делится на четыре квадранта 33×33 с общими кромками).

У OpenMW есть и `Constants::ESM4CellSizeInUnits`, а размер ячейки выбирается по
worldspace (`components/esm/util.hpp`, `getCellSize`) — то есть движок уже умеет обе сетки.

## Запись `LAND`

Порядок сабрекордов при записи (`Land::save`, `components/esm3/loadland.cpp:134`):

1. `INTV` — 8 байт: `x` (i32), `y` (i32) — индексы ячейки
2. `DATA` — 4 байта: флаги (u32)
3. `DELE` — только если запись удалена
4. `VNML` — нормали
5. `VHGT` — высоты
6. `WNAM` — LOD для карты мира
7. `VCLR` — цвета вершин
8. `VTEX` — индексы текстур

Флаги в `DATA` (`Land::Flags`): `Flag_HeightsNormals = 0x1`, `Flag_Colors = 0x2`,
`Flag_Textures = 0x4`.

Размеры сабрекордов (65×65 = 4225 вершин, 16×16 = 256 патчей):

| Сабрекорд | Размер | Тип |
|---|---|---|
| `VNML` | 12675 | int8 × 3 × 4225 |
| `VHGT` | **4232** | float (4) + int8 × 4225 + 3 байта padding |
| `WNAM` | 81 | int8 × 81 (сетка 9×9) |
| `VCLR` | 12675 | uint8 × 3 × 4225 |
| `VTEX` | 512 | uint16 × 256 |

Про нормали в комментарии OpenMW честно сказано: «these aren't always correct though.
Edge and corner normals may be garbage» — то есть точность нормалей не критична.

### Кодек `VHGT`

Смещение: `heightOffset = heights[0] / 8`.

Кодирование (`loadland.cpp:155-181`) — дельты по первому столбцу идут между строками,
внутри строки — между соседними столбцами:

```
prev_y = heights[0]
n = 0
for y in 0..64:
    diff = (heights[n] - prev_y) / 8
    data[n] = round_half_away_from_zero(diff)      # diff>=0 ? int(diff+0.5) : int(diff-0.5)
    prev_x = prev_y = heights[n]
    n += 1
    for x in 1..64:
        diff = (heights[n] - prev_x) / 8
        data[n] = round_half_away_from_zero(diff)
        prev_x = heights[n]
        n += 1
```

Декодирование (`loadland.cpp:315-347`):

```
row = heightOffset
for y in 0..64:
    row += data[y*65]
    heights[y*65] = row * 8
    col = row
    for x in 1..64:
        col += data[y*65 + x]
        heights[x + y*65] = col * 8
```

Замечания:

- первая дельта `data[0]` всегда 0 — значение строки 0 несёт `heightOffset`
- округление **от нуля** (`+0.5` / `-0.5`), а не банковское; для бит-в-бит round-trip это важно
- дельта не может превысить ±127 (то есть ±1016 юнитов между соседними вершинами).
  При слиянии 2×2 это ограничение соблюдается автоматически, потому что оно соблюдалось
  в исходнике с тем же шагом вершины

### Перестановка `VTEX`

`transposeTextureData` (`loadland.cpp:31-39`) — перестановка блоками 4×4:

```
readPos = 0
for y1 in 0..3:
  for x1 in 0..3:
    for y2 in 0..3:
      for x2 in 0..3:
        out[(y1*4 + y2)*16 + (x1*4 + x2)] = in[readPos++]
```

В базе 4 это обмен двух разрядов индекса (`y1 x1 y2 x2` → `y1 y2 x1 x2`), то есть
перестановка — **инволюция**: одна и та же функция работает в обе стороны. OpenMW так её
и использует — и при чтении, и при записи.

Индексы текстур: **при поиске `LTEX` из индекса надо вычесть 1**; индекс 0 означает
текстуру по умолчанию (комментарий в `landrecorddata.hpp`).

**Перестановку обязаны делать мы, библиотека её не делает.** Прочитано 2026-09-19 в
`Greatness7/tes3`, `libs/esp/src/types/landscape.rs`: `TextureIndices` — это
`Box<[[u16; 16]; 16]>`, который грузится и сохраняется как есть, 512 байт подряд. То есть
библиотека отдаёт и принимает **дисковый** порядок, тогда как OpenMW переставляет и на
чтении, и на записи, и в памяти держит геометрический. Передать библиотеке геометрическую
сетку — значит перемешать текстуры блоками 4×4 и не получить ни ошибки, ни предупреждения.
Реализация с этой оговоркой: `crates/transform/src/land.rs::transpose_texture_data`.

Побочно оттуда же: `decode_vertex_heights` библиотеки — независимая от OpenMW реализация
того же кодека `VHGT` (цикл слит в один проход, `offset` сбрасывается в `heights[y][0]` на
каждой строке), и она даёт тот же результат. Два независимых читателя, согласных между собой,
— настолько надёжное подтверждение раскладки, насколько это возможно без ванильного движка.

Патч текстуры = 8192 / 16 = **512 юнитов**, одна текстура на патч, альфа-смешивания нет.
В TES4/TES5 на ячейку 4 квадранта, у каждого базовая текстура (`BTXT`) плюс до 8
альфа-слоёв (`ATXT` + `VTXT`) с сеткой прозрачности 17×17 — то есть примерно 128 юнитов на
отсчёт прозрачности. Разрешения источника хватает, чтобы посчитать на каждый 512-юнитовый патч
TES3 текстуру, которой в нём видно больше всего (правило — `formats/tes4.md`, «Внешний мир →
Morrowind»), но само смешивание теряется.

### Генерация `WNAM`

`generateWnam` (`loadland.cpp:362-380`) — сетка 9×9 для карты мира:

```
vertMult = (65 - 1) / 9        # = 7.111…
for row in 0..8:
  for col in 0..8:
    h = heights[int(row*vertMult)*65 + int(col*vertMult)]
    h /= 128.0 if h > 0 else 16.0
    wnam[row*9 + col] = clamp(h, -128, 127) as int8
```

Асимметричный делитель (128 над водой, 16 под водой) — не опечатка, так в оригинале.

## Записи, нужные для первого этапа

Порядок при записи взят из соответствующих `save()`.

**`LTEX`** (`loadltex.cpp:48`): `NAME` (строковый ID) → `INTV` (индекс, u32) →
`DATA` (путь к текстуре) → `DELE` при удалении.
Индекс — тот самый, на который ссылается `VTEX` (со сдвигом на 1).

**`STAT`** (`loadstat.cpp:41`): `NAME` (строковый ID) → `MODL` (путь к мешу).
Всё; это самая простая запись, с неё удобно начинать сквозной прогон.

**`CELL`** (`loadcell.cpp:194`): `NAME` (имя ячейки) → `DATA` (композит) → далее по типу:
- интерьер: `WHGT` (уровень воды, float), `RGNN` (регион), `AMBI` (композит освещения)
- экстерьер: `RGNN`, `NAM5` (цвет на карте)
- `NAM0` — счётчик временных ссылок (пишется отдельно, `saveTempMarker`)

`DATA` — 12 байт: флаги (i32), `gridX` (i32), `gridY` (i32).
Флаг `Interior = 0x01`; `isExterior()` — это просто отсутствие этого флага.

**В записях плагина — наоборот, путь с подкаталогом**, относительно своей папки:

|---|---|---|

### Следствие для T1.6, и оно неприятное

Меши можно складывать в свой подкаталог (`Meshes\ob\…`) и ссылаться на него из записи, а
**текстуры так развести нельзя**: в NIF уходит одно имя без каталога, значит все текстуры
Oblivion ложатся в `Textures\` плоско, и столкновения имён при уплощении дерева каталогов
источника не гипотетические, а неизбежные. Разведение имён текстур обязано быть таким же
детерминированным, как схема ID (`transform/ids.rs`), и по той же причине: переименование
текстуры между прогонами ломает уже собранные меши.

**Не проверено:** примет ли ванильный движок подкаталог в пути к текстуре внутри NIF. Два
случая из 9170 говорят, что да, но это мод, а не ваниль, и оба случая — с префиксом от
`Data Files\`. До проверки на реальной игре пишем голое имя: оно работает заведомо.

## Предел длины `MODL`: 31 знак плюс нуль — измерено Construction Set

**Наблюдал владелец 2026-09-24**, открыв в Construction Set плагин, собранный по старому правилу
пути (`ob\` + путь источника целиком):

```
Chunk size 73 too big in chunk MODL_ID in form STAT_ID. Max size is 32,
data truncated to "ob\00tamrext\armor\darksoulsser".
```

То есть CS держит `MODL` в буфере на **32 байта, включая завершающий нуль**: больше 31 знака
он обрезает. Обрезанный путь указывает на несуществующий файл, а сохранённый из CS плагин
теряет модель насовсем. Принимает ли длинный путь сам движок — не проверялось, и это уже не
важно: плагин обязан открываться в CS.

**Ваниль и моды держат тот же предел.** Измерено 2026-09-24 скриптом по сабрекордам `MODL`
всех записей: `Morrowind.esm` (9 499), `Tribunal.esm` (1 313), `Bloodmoon.esm` (1 819) и два
плагина мод-пака `MW/Data Files` (66) — всего **12 697 `MODL`, длиннее 32 байт с нулём ни
одного**. Максимум — ровно 32 (`x\Ex_velothi_striderport_01.NIF`,
`m\Misc_Com_Pitcher_Metal_01.NIF`, `x\Ex_DAE_ruin_stair01_short.nif`).

По оружию ванили (548 `WEAP`, Morrowind + DLC) максимум `FNAM` — **31**, `ITEX` — **30**. Предел
CS для `FNAM` и `ITEX` не измерялся; 31 — граница, которую ваниль заведомо держит.

**Как устроено у нас.** Короткий путь `ob\<имя>_<хеш>.<расш>` ([tes4.md](tes4.md), «Короткие
пути»), и `tes3_out::PluginBuilder` отказывается писать `MODL`, `ITEX` или `FNAM` длиннее 31
знака (`MAX_FIELD_LEN`), а не обрезает их.

## Предел длины ID актёра: 23 знака — измерено Construction Set

ID записи `NPC_` и `CREA` не может быть длиннее **23 знаков**. Construction Set при загрузке плагина
пишет на каждую такую запись «The name for NPC '…' exceeds 23 characters» (так же для Creature) —
найдено владельцем 2026-10-02 на `SEWorld.esp`: 475 записей из 550. У ванили самый длинный ID
актёра — ровно 23 у обоих типов (`centurion_shock_baladas`, `esib-nummu assunudadnud`;
`tes3_out/tests/real_vanilla_ids.rs`), у остальных типов — до 31. Причина предела: к ID актёра
движок дописывает восемь цифр номера экземпляра, и вместе они занимают те же 31 знак.

**Как устроено у нас.** `transform::ids::IdAllocator::allocate_actor`: тот же вид
`ob_<имя>_<FormID в base36>`, но не длиннее 23 — на читаемую часть остаётся 12 знаков. Из имени
выбрасываются слова `Creature` (в любом регистре) и `NPC` (заглавными): в `EDID` Oblivion они только
называют тип записи (`SECreatureGnarlMania` → `ob_SEGnarlMania_…`). Уникальность по-прежнему держит
суффикс FormID. Прочие записи (в том числе списки существ `LEVC` и части тела голов NPC) берут
прежний бюджет 31. Прогон `SEWorld` (2026-10-02): 372 `NPC_` и 178 `CREA`, самый длинный ID — 23.

## Имя узла `Collision…`: корень с таким именем роняет Construction Set

**Найдено 2026-10-02** по дампу падения Construction Set 1.6.0.1820 (с CSSE): владелец открыл ячейку
`Hill of Suicides` плагина `SEWorld.esp`, редактор вылетел без сообщений — `0xC0000005` в
`ntdll.dll`, в `Warnings.txt` ничего. В дампе — исчерпанный стек: 23 466 кадров одной функции
(`0x5B6D20`, сбор свойств вверх по цепочке родителей), и во всех кадрах один и тот же узел, то есть
узел сцены стал **собственным родителем**.

Как это получается (дизассемблер, функция `0x54AAC0`): загружая модель объекта, редактор обходит
дерево и сравнивает начало имени каждого узла со строкой `Collision` — девять знаков, без учёта
регистра. Узел с таким именем он переносит в отдельный узел коллизии объекта, который создаёт сам и
вешает под **корень** модели. Если `Collision…` называется сам корень, в узел коллизии переносятся
дети корня — в том числе только что повешенный узел коллизии. Дальше обход свойств вверх по
родителям не кончается.

В `SEWorld` так названы корни двух мешей Oblivion — невидимых стенок `CollisionBox01` и
`CollisionBoxStatic` (`meshes\dungeons\misc\`): 363 ссылки в 13 ячейках снаружи и 44 интерьерах.
Редактор падает, когда загружает модель такого объекта. В самих четырёх ячейках `Hill of Suicides`
(47…48, 3…4) этих ссылок нет, ближайшие — в ячейке (45, 5), через одну: редактор грузит и
окрестность открытой ячейки (какого размера — не измерялось). У ванильных мешей таких имён корня
нет (`Morrowind.esm` в редакторе открывается). Имя на `Collision` у внутреннего узла
(`CollisionGarlic01` в `floragarliccluster.nif`) к падению не ведёт, но узел уезжает в узел
коллизии.

**Как устроено у нас.** `mesh_convert::node_name`: перед именем узла, начинающимся на `Collision`,
ставится `ob_` — у корня, внутренних узлов, форм и узлов частиц мировых объектов. По именам этих
узлов Morrowind ничего не ищет. Скелеты существ и тел идут мимо (их кости ищутся по имени); имён на
`Collision` среди них нет — проверено по всем 3 082 мешам прогона `SEWorld` (2026-10-02).

**Не проверено:** делает ли то же движок игры; открывается ли ячейка в редакторе после правки —
предстоит проверить в игре и в редакторе.

## Повторные ссылки: Construction Set убирает их сам

При загрузке плагина Construction Set убирает ссылку, если в той же ячейке уже стоит тот же объект
в той же точке с тем же поворотом, и пишет в `Warnings.txt`:

```
Duplicate "ob_RockDementiaSm03_0001ofh" (404785,55492,3032) in cell Puddlejump Camp from file SEWorld.esp removed.
84 duplicate references were removed.
```

У `SEWorld.esp` таких было 84 (владелец, 2026-10-02): в 25 ячейках снаружи и 19 интерьерах. Это не
ошибка слияния городов — пары стоят так в самом `Oblivion.esm`: автор поставил камень, гриб или
потолок руин дважды. 73 пары совпадают до бита, 11 — нет.

**Критерий** снят с этих 84 строк перебором допусков по ссылкам плагина: по каждой оси позиции
разница **меньше 1 юнита**, по каждому углу — **меньше 0.01 рад**, ID объекта тот же. Он даёт ровно
те же 84 ссылки в тех же ячейках; допуск 0.5 юнита или 0.005 рад теряет одну (тарелки в `Vitharn
Keep`: 0.92, 0.37 и 0.97 юнита по осям, 0.008 рад). Верхние границы допусков этим набором не
пойманы: 2 юнита и 0.1 рад дают те же 84. Масштаб у всех пар одинаковый — сравнивает ли его
редактор, не видно.

**Как устроено у нас.** `transform::exterior` (`Twins`): вторая такая ссылка в ячейке выхода не
ставится — тот же ID, те же допуски, тот же масштаб; остаётся ссылка с меньшим `FormID`. Номера
ссылок идут подряд, без дыр. Прогон `SEWorld` (2026-10-02): не поставлено 84, ссылок 108 284,
повторных по этому критерию в плагине 0.

**Не проверено:** убирает ли такие ссылки движок игры.

## Запись `WEAP`

Порядок сабрекордов при записи (`Greatness7/tes3`, `libs/esp/src/types/weapon.rs`): `NAME` →
`MODL` → `FNAM` → `WPDT` → `SCRI` → `ITEX` → `ENAM` → `DELE`.

`WPDT` — 32 байта:

| Смещение | Тип | Поле |
|---|---|---|
| 0 | f32 | вес |
| 4 | u32 | цена |
| 8 | u16 | тип (0–13, ниже) |
| 10 | u16 | прочность |
| 12 | f32 | скорость |
| 16 | f32 | дальность |
| 20 | u16 | ёмкость зачарования |
| 22 | u8 × 6 | chop min/max, slash min/max, thrust min/max |
| 28 | u32 | флаги: `0x1` — игнорирует обычную сопротивляемость оружию, `0x2` — серебро |

Типы: 0 короткий клинок, 1 длинный клинок 1H, 2 длинный клинок 2H, 3 дробящее 1H,
4 дробящее 2H (близко), 5 дробящее 2H (широко, посохи), 6 копьё, 7 топор 1H, 8 топор 2H,
9 лук, 10 арбалет, 11 метательное, 12 стрела, 13 болт.

Модель у оружия одна — и в руке, и на земле. Иконка `ITEX` относительно `Icons\`. Как
пересчитываются поля из Oblivion — [tes4.md](tes4.md), «`WEAP` → `WEAP`».

## Экстерьер: одна сетка, практически бесконечная

**Поля worldspace в `ESM::Cell` нет вообще** (`loadcell.hpp`). Есть только:

```
struct DATAstruct {
    int32_t mFlags;        // Interior = 0x01
    int32_t mX, mY;        // индексы ячейки
};
```

Ключевой факт: **`mX`/`mY` — `int32`**. То есть сетка экстерьера охватывает такой диапазон,
что свободного места в ней неограниченно много. Экстерьер в TES3 — один, но практически
бесконечный. Интерьеры адресуются по имени (`mName`), они вне сетки.

Отсюда способ разместить несколько worldspace источника: не превращать их в интерьеры, а
**разносить смещением** по единой сетке. Смещение — чистая арифметика:

| Что сдвигать | Как |
|---|---|
| `CELL.DATA` → `gridX`, `gridY` | `+ dx`, `+ dy` |
| `LAND.INTV` → `x`, `y` | `+ dx`, `+ dy` |
| мировые координаты каждого размещения | `x + dx*8192`, `y + dy*8192` |
| Z и координаты внутри ячейки | не трогаются |

**Занято ванилью** (2026-09-25, `tes3_out/tests/real_vanilla_grid.rs`): `Morrowind.esm` — 1 404
внешних ячейки, x −18…23, y −19…27; `Tribunal.esm` — 18, x −16…4, y −14…8 (без `LAND`);
`Bloodmoon.esm` — 173, x −29…−2, y −8…28. Вместе x −29…23, y −19…28. Смещение по умолчанию
(`pipeline::default_offset`) ставит западный край worldspace на x = 32 (зазор 8), южный — на
y = −19. Моды (Tamriel Rebuilt и др.) не учитываются — сканер занятых ячеек в фазе 5.

### Размер активной области — важное следствие для плотности

`components/misc/constants.hpp`:

```
CellSizeInUnits      = 8192    // ячейка TES3
ESM4CellSizeInUnits  = 4096    // ячейка TES4/TES5
CellGridRadius       = 1       // TES3: активны (2*1+1)² = 3×3 ячейки
ESM4CellGridRadius   = 2       // TES4/TES5: активны 5×5 ячеек
UnitsPerMeter        = 69.99125109
UnitsPerFoot         = 21.33333333
```

Считаем нагрузку по ссылкам при слиянии 2×2: активны 9 ячеек TES3, в каждой содержимое
4 ячеек источника → **36 ячеек Oblivion одновременно против 25**, которые держит сам
Oblivion. То есть примерно **1.44×** к исходной нагрузке по числу активных ссылок, а не
просто 4× на ячейку. Это надо проверять стресс-плагином до того, как вкладываться в
конвертацию большого региона.

Радиусы взяты из OpenMW и описывают его поведение; у ванильного движка размер активной
сетки надо подтвердить отдельно, но соотношение размеров ячеек от движка не зависит.

**`TES3`-заголовок** (`loadtes3.hpp`): `HEDR` несёт версию, `type` (i32: 0 = esp, 1 = esm,
32 = ess), автора, описание и число записей; затем на каждый мастер пара
`MAST` (имя файла) + `DATA` (размер, u64).

## NPC и части тела: морфинга нет, всё статическое

Это решает вопрос, выполним ли перенос лиц из Oblivion.

**`ESM::NPC`** (`components/esm3/loadnpc.hpp`):

- `RefId mId, mRace, mClass, mFaction, mScript`, `std::string mName`
- **`RefId mHair, mHead`** — ссылки на части тела, **у каждого NPC свои**
- `NPDTstruct52`: карты атрибутов и навыков (`unsigned char` на каждый),
  `uint16_t mHealth, mMana, mFatigue`; есть также вариант `NPDTstruct12` для autocalc,
  какой именно — различает `mNpdtType`
- перечисления `Services`, `Flags`, `NpcType`

**`ESM::BodyPart`** (`components/esm3/loadbody.hpp`):

```
BYDTstruct { unsigned char mPart, mVampire, mFlags, mType; }
RefId mId, mRace;
Path  mModel;        // просто путь к NIF
```

Слоты `MeshPart` — **15 штук**: `MP_Head = 0`, `MP_Hair = 1`, `MP_Neck`, `MP_Chest`,
`MP_Groin`, `MP_Hand`, `MP_Wrist`, `MP_Forearm`, `MP_Upperarm`, `MP_Foot`, `MP_Ankle`,
`MP_Knee`, `MP_Upperleg`, `MP_Clavicle`, `MP_Tail`.
`MeshType`: `MT_Skin = 0`, `MT_Clothing = 1`, `MT_Armor = 2`.
`Flags`: `BPF_Female = 1`, `BPF_NotPlayable = 2`.

**Полей морфинга нет нигде.** Голова в TES3 — это статический NIF по пути в `mModel`,
и не более того.

### Следствие для лиц Oblivion

В Oblivion лицо вычисляется в рантайме: запись `NPC_` несёт коэффициенты FaceGen
(`FGGS` — симметричная геометрия, `FGGA` — асимметричная, `FGTS` — текстура), базис морфинга
лежит в порасовых `EGM`/`EGT`, применяет FaceGen SDK, статически влинкованный в
`Oblivion.exe`.

Раз в TES3 голова статическая, а на каждого NPC можно указать свою — правильный путь это
**запечь**: применить базис с коэффициентами конкретного NPC, получить уникальный меш и
текстуру, выписать на него отдельную запись `BODY` с `MP_Head` и направить туда `mHead`.
Отсутствие морфинга в движке перестаёт иметь значение, когда меш уже morphed.

Вниз это легче, чем вверх: референсу для Skyrim нужно заново порождать данные FaceGen в
системе Skyrim, и его `TODO.txt` фиксирует, что это не сделано («…turn FGGS/FGGA coefficients
into real vertex deltas»). Для нас «real vertex deltas» и есть конечный результат.

Нерешённое: **формат `EGM`/`EGT` в этой сессии не проверялся** — его надо реверсить или
применять базис через харнесс над кодом самого Oblivion.

Побочно: эти же 15 слотов `MP_*` плюс `MT_Armor`/`MT_Clothing` — готовая цель для разбора
скиннингованной брони Oblivion на жёсткие части.

## Ссылки актёров — постоянные (2026-09-30)

Ссылки ячейки делятся на постоянные (до `NAM0`) и временные (после; `NAM0` — их число). В
`Morrowind.esm` **все** 3 043 ссылки на `NPC_` и 863 на `CREA` постоянные. `SEWorld.esp` с 285
NPC во временном разделе загружался, NPC стояли и «дышали», но не ходили, а разговор с любым ронял
игру: функция активации (`Morrowind.exe+0xEAB3F`, рядом строки `WolfNPC1`, `Companion`) берёт у
ссылки вложение типа 8 (mobile actor), а его нет, и читает поле по нулевому указателю. Библиотека
`tes3` сама пишет об этом в `Reference::persistent`: «NPCs and creatures should also always be
persistent. We do not have the information to enforce that here». Поэтому признак ставит конвейер:
`BaseObject::Placed::actor` → `tes3_out::Reference::persistent`. Что с постоянными ссылками NPC
ходят и говорят — **не проверено** в игре. Двери с назначением библиотека делает постоянными сама.
Ссылка на список существ `LEVC` — наоборот, временная (все 7 478 у трёх мастеров, T11.4; раздел
«Уровневые списки существ» ниже).

## Прочие подтверждённые факты

**Диалоги переносимы вместе с озвучкой.** В `ESM::DialInfo` (`loadinfo.hpp`) есть поля
`mSound` (файл озвучки), `mResponse`, `mResultScript`, `mQuestStatus`, условия `mSelects`,
а также фильтры по рангу, полу и расположению. То есть на каждую реплику TES3 можно
навесить голосовой файл. Lip sync в TES3 отсутствует — генерация `.lip` не нужна.

**Havok → игровые юниты: множитель 7.** В Oblivion havok-координаты равны игровым,
делённым на 7 (`asset_convert/collision/collision_extract.py:43` в референсе:
«7 game-units-per-havok-unit»). При разборе `bhk*`-фигур в треугольники для
`RootCollisionNode` координаты надо умножать на 7. Отдельно: в кодировании констрейнтов
Skyrim референс применяет свой множитель 0.1 (`collision_constraints.py:22`).

**`LEVI`: флаги переставлены относительно Oblivion, числа у строки нет.** `DATA` (u32): 0x1 —
бросок на каждую единицу числа в контейнере, 0x2 — все уровни ≤ игрока; у `LVLF` Oblivion
наоборот. Так называет биты и `Greatness7/tes3` (`LeveledItemFlags`), и независимый `esmtool`
(«Each» 0x1, «AllLevels» 0x2); `Morrowind.esm`: 227 `LEVI`, 0x1 у 136, 0x3 у 67, 0x2 у 11, 0 у
13 (2026-09-27). `NNAM` — шанс «ничего» (1 байт), строки — пары `INAM` (ID) + `INTV` (u16
уровень); числа у строки нет — поэтому ваниль кладёт в списки монеты-номиналы `Gold_005…100`
(`docs/ru/formats/tes4.md`, «Уровневые списки»).

### Сетки путей (`PGRD`, T4.1)

Раскладка — `tes3::esp::PathGrid`: `DATA` 12 байт (сетка ячейки i32×2, `Granularity` u16, число
точек u16), `NAME` — имя ячейки, `PGRP` — точки по 16 байт (x, y, z i32, «автогенерирована» u8,
число связей u8, 2 байта заполнения), `PGRC` — номера соседей u32 подряд, в порядке точек.
Число связей точки — один байт, то есть не больше 255.

По `Morrowind.esm` (2026-09-27, `esmtool dump -t PGRD` и скрипт по файлу):

- 1 194 `PGRD`; точек в одной сетке до **246**.
- **Внешние точки — от юго-западного угла ячейки**, 0…8192 (у Oblivion — мировые). Интерьеры —
  сетка (0, 0), координаты ячейки.
- **Каждое ребро записано у обоих концов** (у точки 1 → 0 есть 0 → 1).
- **`NAME` никогда не пуст:** у именованной внешней ячейки — её имя («Balmora» у (−2, −2) и
  (−3, −2)), у безымянной — имя региона («Azura's Coast Region»), у интерьера — имя ячейки.
- `Granularity` 1024 у 737 записей, дальше 256 (265), 2048 (88), 128 (51), 512 (29), 4096 (17),
  единичные 0, 101, 114, 121, 29811. Шаг автогенерации CS, движку, судя по разбросу, не важен.
- «Автогенерирована» = 1 у 37 253 точек из 41 745 (89 %). У нас — 1 у всех (решение владельца
  2026-09-27).
- **Порядок:** `PGRD` идёт сразу за своей `CELL` (1 060 раз) или её `LAND` (134). Мы пишем все
  `PGRD` после всех `CELL` и `LAND`. OpenMW (`apps/openmw/mwworld/store.cpp`,
  `Store<ESM::Pathgrid>::load`, 2026-09-27) связывает сетку с внешней ячейкой по сетке из `DATA`,
  а с интерьером — по `NAME`, если сетка (0, 0) **и ячейка с таким именем уже загружена**; значит,
  `PGRD` должна идти после своей `CELL` — у нас так. Внешняя ячейка с сеткой (0, 0) и именем,
  совпавшим с интерьером, была бы принята за интерьер; со смещением по умолчанию внешних (0, 0) у
  нас нет. Ванильный движок — не проверено.

### Звуки (`SOUN`, T10.1)

Раскладка — `tes3::esp::Sound`: `FNAM` — путь относительно `Sound\`, `DATA` — 3 байта: громкость
(0…255 = 0…1) и дальность min, max. По `Morrowind.esm` (2026-09-28, скрипт по файлу через `tes3`,
`esmtool dump -t SOUN`/`GMST`):

- 430 `SOUN`; громкость 255 у 350, прочие 51…229.
- Дальность **0/0 у 357** — умолчания движка (GMST `fAudioDefaultMinDistance` 5,
  `fAudioDefaultMaxDistance` 40); прочие пары — от (1, 2) до (255, 255), чаще (30, 100), (10, 50),
  (5, 30).
- Множители дальности: `fAudioMinDistanceMult` **20**, `fAudioMaxDistanceMult` **50**; то есть
  (30, 100) — 600 и 5 000 единиц. Что движок умножает именно так (и 0/0 → умолчания) — по коду

### Скрипты (`SCPT`, T10.3)

Ванильный движок исполняет байт-код `SCDT`, текст `SCTX` — только для CS. `SCHD` — ID (32 байта с
нулём), число `short`/`long`/`float`, длина `SCDT`, длина `SCVR`; `SCVR` — имена переменных, каждое
с нулём. Разобрано по парам `SCTX` ↔ `SCDT` `Morrowind.esm` (2026-09-28, скрипт по файлу):

- Код инструкции — `u16` LE: `End` `01 01`, `If` `06 01`, `EndIf` `09 01`, `PlayLoopSound3DVP`
  `2f 11`. После `If` — байт «сколько инструкций пропустить, если ложно», байт длины выражения и
  выражение **текстом**, где вызов функции — `X` и её код (`CellChanged` `1f 10`,
  `GetSoundPlaying` `88 11`, за ним ` b` и байт длины + ID звука; смысл ` b` не выяснен — переписан
  как у ванили). `PlayLoopSound3DVP`: байт длины, ID звука, два `f32` (громкость, тон).
- У всех 22 скриптов `Sound_*` `Morrowind.esm` с `PlayLoopSound3DVP` байт-код один и тот же,
  меняются только длина и ID звука и два `f32`; длина `SCDT` = 46 + 2·длина ID. Регистр и запятые
  в тексте на байт-код не влияют (`lava`: `"lava layer", 1.0, 1.0` — те же байты).
- Скрипт из одних `short` (`nohello`, `noflee`, `LocalState`, …): `SCDT` = `01 01`, имена — в
  `SCVR`, число — в `SCHD`.

Наши шаблоны (`tes3_out::Script`): `LoopSound` (громкость и тон 1.0) и `Locals`. Сверка —
`tes3_out/tests/real_vanilla_scripts.rs` (2026-09-28): побайтово совпали **12** петель (все
скрипты `Sound_*` с громкостью 1.0: `Sound_Cave_Drip`, `Sound_Machinery`, …) и **28** скриптов из
одних `short` (`SCDT`, `SCVR` и число переменных). Исполнит ли ванильный движок наш байт-код так
же — ⛔ (T10.4).

### Двери (`DOOR`, T2.6)

В меше двери Morrowind движения нет: ни у одной из 76 дверей `Morrowind.esm` нет ни
`NiKeyframeController`, ни последовательностей (замер tes4skyrim, у нас не повторён). Дверь без
телепорта движок поворачивает сам (OpenMW, `World::rotateDoor`, `mwclass/door.cpp`): к углу Z ссылки
добавляется 90° за 1 с; ось — вертикаль через начало координат меша. Дверь-телепорт не
поворачивается вовсе: активация уходит в телепорт раньше.

**Углы ссылки.** `DATA` ссылки — три угла в радианах; OpenMW (`makeObjectOsgQuat`) строит ориентацию
поворотами вокруг **−Z, −Y, −X**, сначала Z. Положительный угол Z — поворот по часовой стрелке, если
смотреть сверху: ось +X меша уходит к −Y мира. Значит, открытая дверь Morrowind — закрытая,
повёрнутая на 90° по часовой, то есть на −90° вокруг +Z меша. По этому правилу
`transform::exterior::reference_offset` переводит вектор кадра меша в мир. Порядок осей у
наклонённых ссылок в ванильном движке **не проверен**; из 700 ссылок на двери в `SEWorld`
наклонены 7.

**Перенос петли** (какие двери — `formats/nif-oblivion.md`, «Двери: что двигает `Open`»). Начало
координат меша сдвигается в петлю h = (x, y, 0); чтобы дверь не уехала, позиция ссылки становится
p′ = p + s·R·h, где s — масштаб ссылки, R — её поворот. Пример, посчитанный вручную (2026-10-02):
дверь Деменции `SEDemDoorAnim01`, ссылка `0005E348` — p = (438.46, 505.93, −152.79), угол Z = −π/2,
s = 1.01; петля h = (48.79, 2.90, 0). Угол −π/2 «по часовой» — это 90° против часовой:
(x, y) → (−y, x) = (−2.90, 48.79), на масштаб — (−2.93, 49.28); p′ = (435.53, 555.22, −152.79). То же
выдаёт конвейер (`back2mw/tests/real_doors.rs`: сдвиг ссылки (−2.9289, 49.2816, 0)).

**Не проверено** в игре: что дверь с перенесённой петлёй стоит в проёме и поворачивается вокруг
петли; учитывает ли движок преобразование корневого узла меша — поэтому сдвигаются дети корня, а не
сам корень.

### Диалоги (`DIAL`/`INFO`, T10.6)

Измерено по `Morrowind.esm` (2026-09-28, разовый скрипт по файлу; `Tribunal.esm`/`Bloodmoon.esm` —
для `INAM`). Писатель — `tes3_out::dialogue`, перевод — `transform::dialogue::convert`.

- **Порядок.** `DIAL` и сразу его `INFO`; все темы — в конце файла. `DIAL` `DATA` — 1 байт: 0 тема
  (1 698), 1 голос (8), 2 приветствие (10: `Greeting 0`…`Greeting 9`), 3 убеждение (10), 4 журнал
  (632). Имя темы — её ID; самое длинное — 36 знаков.
- **`INAM`** — только цифры, без ведущего нуля, 12…20 знаков. Уникален **в пределах темы**: между
  темами у `Morrowind.esm` 211 повторов, у `Bloodmoon.esm` 8. `PNAM`/`NNAM` — соседи; у первой
  реплики темы `PNAM` пуст.
- **`NAME`** (текст) — без нуля в конце, не длиннее **512** (ровно 512 — у двух реплик).
- **`DATA` реплики** — 12 байт: тип темы `u32`, отношение `i32`, ранг говорящего `i8`, пол `i8`
  (−1 любой, 0 мужской, 1 женский), ранг игрока `i8`, байт-заполнитель. −1 — «не проверяется».
- **`SCVR`** — не больше **6** на реплику (у 64 ровно 6). Строка: номер слота `'0'…'5'`, тип, два
  знака функции, операция (`'0'` `==`, `'1'` `!=`, `'2'` `>`, `'3'` `>=`, `'4'` `<`, `'5'` `<=`),
  имя. За `SCVR` — `INTV` (у функций, предметов, `short`/`long`) или `FLTV` (у `float`-переменных).
  Виды у ванили: `1` + номер функции (`138` PC Sex, `150` Choice, `163` Talked to PC…), `2sX`/`2fX`
  глобальная (`12fX3GameHour`), `3sX`/`3fX` локальная, `4JX` журнал, `5IX` предмет
  (`5IX4Gold_001 = 200` — так ваниль проверяет золото игрока), `6DX` убитые, `7XX` Not ID, `8FX` Not
  Faction, `9CX` Not Class, `ARX` Not Race, `BLX` Not Cell, `CsX` Not Local.
- **Not-фильтры** у ванили стоят и с `= 1`, и с `= 0`; мы пишем `= 1` в смысле «говорящий не X»
  (так понимает OpenMW; в ванильном движке — ⛔ T10.9).
- **PC Sex** (38): у ванили `= 1` в репликах к женщине («Young lady…») — 1 значит женский.
- **Choice** у ванили и в приветствиях: фильтр `Choice` (150) в `Greeting 0` — 9 реплик,
  `Greeting 5` — 75. Выбор ищет реплику снова в той же теме.
- **Глобальные** с тем же именем, что у Oblivion: `GameHour` (`f`), `TimeScale` (`f`); у дня, месяца,
  года имена другие (`Day`, `Month`, `Year`), `Random100` — `s`.
- **Вставка в тему мастера**: наш блок — в начало, `PNAM` первой нашей пуст, `NNAM` последней —
  первая реплика мастера (как пишет CS). Что ванильный движок ставит блок именно в начало — ⛔ T10.9.
- **Голос и убеждение** (T10.7, замер 2026-09-29 по `Morrowind.esm`/`Tribunal.esm`/`Bloodmoon.esm`):
  темы Voice — `Alarm`, `Attack`, `Flee`, `Hello`, `Hit`, `Idle`, `Intruder`, `Thief`; Persuasion —
  `Admire`/`Bribe`/`Intimidate`/`Taunt` × `Success`/`Fail`, `Info Refusal`, `Service Refusal`. Своих
  тем этих типов плагин не заводит: движок спрашивает их по имени. У голоса **текст есть ровно у
  реплик со звуком** (`SNAM`), реплики без звука — пустые заглушки по фильтрам (`Hello` 3 239 со
  звуком из 3 260). У убеждения звука нет ни у одной реплики. Числа по темам — `tasks/phase-10.md`,
  T10.7.

### Окно карты (карта мира для MWSE, `back2mw::world_map`)

**Границы карты мира.** Карта мира у движка одна. По описанию опции «Map expansion (for Tamriel
Rebuilt)» в самом Morrowind Code Patch (`mcpatch\describe.json`, 2026-10-02): исходная карта — ячейки от
(−28, −28) до (28, 28), расширенная — от (−51, −64) до (51, 38), масштаб 5/9 от исходного. Перенесённый
мир со смещением по умолчанию стоит на x = 32…63. В игре границы не измерялись.

**Элементы окна.** Имена — строки `Morrowind.exe` (Steam GOTY, 2026-10-02); ими пользуется
`tes3ui.registerID` MWSE. Вложенность элементов в игре не проверялась.

| Имя | Что это, судя по имени |
|---|---|
| `MenuMap` | само окно |
| `MenuMap_world`, `MenuMap_local` | карта мира и локальная карта; переключает их `MenuMap_switch` |
| `MenuMap_world_panel`, `MenuMap_world_pane`, `MenuMap_world_map` | прокрутка и картинка карты мира |
| `MenuMap_world_marker`, `MenuMap_world_player` | метки мест и метка игрока на карте мира |
| `MenuMap_panel`, `MenuMap_pane`, `MenuMap_map_layout`, `MenuMap_map_cell`, `MenuMap_map_pane`, `MenuMap_local_player` | локальная карта |

**Мод** (`crates/back2mw/src/world_map/main.lua`, в игре — `MWSE\mods\back2mw\map\main.lua`):

- на `initialized` читает все `worlds\*.json` (`json.loadfile`, формат — [tes4.md](tes4.md), «Карта
  мира»); нет описаний — не подписывается ни на что;
- на `uiActivated` окна `MenuMap`, `loaded`, `cellChanged`, `menuEnter` и раз в секунду, пока окно на
  экране, смотрит, где игрок: снаружи — `tes3.player.position`, в интерьере —
  `tes3.getLastExteriorPosition()`;
- если ячейка игрока попадает в `cells` одного из миров — прячет прямых детей `MenuMap_world` и
  кладёт в него свой блок `back2mw_map` размером с `MenuMap_world` (окошко), в нём — блок
  `back2mw_map_canvas` (лист): картинка (`scaleMode`) и метка игрока — два вложенных прямоугольника
  9×9. Увеличение 1 — лист вписан в окошко с пропорциями файла; начальное — 2, предел — 4 пикселя
  экрана на пиксель листа. Положение листа в окошке и метки на листе — через `absolutePosAlignX/Y`
  (0 — левые края совпадают, 1 — правые): так не нужен знак оси Y у `positionY`;
- колесо (`mouseScrollUp`/`mouseScrollDown`) меняет увеличение, `mouseDown` + `mouseStillPressed` +
  `mouseRelease` с `tes3ui.captureMouseDrag` двигают лист — по `relativeX`/`relativeY` события
  (вниз — плюс: так ими пользуется палитра цветов самого MWSE). У листа, картинки и метки
  `consumeMouseEvents = false`, события доходят до окошка. На `menuEnter` вид встаёт игроком в
  середину; за край листа вид не уходит;
- иначе — возвращает видимость ровно тем элементам, что прятал сам, и прячет свой блок;
- своих текстур у метки нет, чужие элементы окна мод не удаляет и не двигает.

Свои элементы вместо подмены текстуры `MenuMap_world_map` — потому что её размер, масштаб и положение
метки игрока движок пересчитывает сам (и по-разному с патчем карты и без него), а что именно он
переписывает при обновлении окна — неизвестно.

**Проверено в игре** (владелец, 2026-10-02, MWSE 5431, окно карты 1238×677): описание читается,
`MenuMap_world` находится, лист появляется. `MenuMap_world` лежит в окне глубже пятого уровня
(рамка `PartDragMenu_*`, под заголовком — безымянный блок 1230×644).

**Не проверено в игре:** приближение и перетаскивание; обрезается ли лист, который больше окошка,
по границе окошка (на это рассчитано: так устроена пара `MenuMap_world_panel` / `MenuMap_world_pane`
у ванильной карты); положение метки; возврат ванильной карты. Вне игры мод прогоняется на Lua 5.1 с
подставными `tes3`, `tes3ui`, `event`, `timer`, `lfs`, `json` (локальный скрипт, в репозиторий не входит):
чтение описаний, показ и возврат карты, метка, вид по игроку, колесо, перетаскивание, интерьер,
пересоздание окна. При первом показе мод пишет в `MWSE.log` путь от окна до `MenuMap_world` с
размерами и её элементы.

## Скиннинг: соглашение вывода и скелет (T9.2a–b)

**Ваниль носит скиннинговую экипировку.** `NiSkinInstance` есть в 46 из 328 мешей брони
`Morrowind.bsa` (`a\`: кирасы `_c`, перчатки), в 124 из 523 мешей одежды (`c\`: рубашки, юбки) и в
40 из 519 частей тела (`b\`: кожа рас). Ванильная кираса со скиннингом (`lords_cuirass_unique`) —
`ARMO` типа `Cuirass` с **одной** частью тела `Cuirass (3)` → `BODY` (`Part: Chest`, `Type: Armor`)
со скиннинговым NIF. Измерено 2026-09-24.

**Устройство скиннингового NIF ванили** (`a\a_art_cuirass_lords_c.nif`, тест
`mesh_convert/tests/real_skinning.rs`): в файле вся иерархия `Bip01` (65 узлов, в том числе
пальцы 3–4 и `Toe0`, которых у `base_anim` нет) в T-позе; корень скиннинга — узел `Bip01`; общее
преобразование `NiSkinData` — единичное; форма стоит там же, где `Bip01`. Произведение
«форма⁻¹ · кость · обратная поза» у ванили — постоянная (сдвиг ≈ 28.9) для всех костей: экспортёр
записал вершины в собственном кадре.

**Формула движка** — по OpenMW (`components/sceneutil/riggeometry.cpp`, прочитано 2026-09-24):
вершина = (корень скиннинга)⁻¹ · преобразование `NiSkinData` · Σ вес · (кость в пространстве
скелета) · (обратная поза кости) · v. Наш вывод — самое прямое согласованное с ней: узлы костей в
позе привязки Morrowind, вершины в пространстве `Bip01`, форма там же, где `Bip01`,
обратная поза = `(кость)⁻¹ · Bip01`, преобразование `NiSkinData` единичное. Тогда в позе
привязки `Bip01⁻¹ · кость · обратная поза` — единица (проверено деформацией `tes3::nif` на всех
449 мешах: отклонение ≤ 0.000023). **⛔ движок:** что ванильный движок читает так же — не
проверено.

**Скелет.** Набор и иерархия костей — `base_anim.nif` (33 кости `Bip01…`). Но узлы `base_anim`
стоят в **позе анимации** (руки опущены: кисть на высоте 75.7), а не привязки. Поза привязки —
у скиннинговых мешей ванили: тело `b\b_n_imperial_m_skins.nif` (29 костей: без голеней и
ступней) плюс недостающее из кирасы `a\a_art_cuirass_lords_c.nif`. Их позы совпадают во всех общих
костях, кроме пальцев (расхождение до 1.7 — другая поза кисти). Женский скелет в позе привязки
совпадает с мужским.

| Кость (мир, T-поза) | Oblivion | Morrowind |
|---|---|---|
| `Pelvis`, высота | 67.41 | 76.06 |
| `Head`, высота | 112.44 | 118.98 |
| плечо (`UpperArm` → `Forearm`) | 21.85 | 18.01 |
| предплечье (`Forearm` → `Hand`) | 14.78 | 16.94 |
| бедро (`Thigh` → `Calf`) | 33.67 | 32.63 |
| голень (`Calf` → `Foot`) | 27.33 | 37.14 |

Позы Oblivion — по данным референса (`asset_convert/generated/skeleton_bones_*.json`), позы
Morrowind — наш тест; обе стороны сходятся с T-позой ванильных файлов.

**Имена форм — обязательны.** Надетую скиннинговую часть тела движок рисует только из форм с
именем `Tri <узел слота>` (регистр неважен, дальше может идти номер): узел — имя слота `INDX` в
`base_anim.nif` (`Head`, `Chest`, `Groin`, `Right Hand`, `Left Hand`, `Right Foot`, `Left Foot`,
`Shield Bone`, …; узла `Hair` нет — волосы садятся на `Head`, так же у OpenMW
`NpcAnimation::getBonename`). Форма с другим именем молча выбрасывается — вещь на теле невидима,
а мировая модель и превью CS при этом в порядке. Ваниль (`Morrowind.bsa`, скиннинговые `BODY`,
2026-09-25): у груди 509 форм `Tri Chest`, у кистей 130 `Tri Right Hand` и 110 `Tri Left Hand`,
у ступней `Tri Right Foot`/`Tri Left Foot`; скиннинговых голов в ванили нет. Проверено в игре
(оригинальный движок, 2026-09-25): шлемы, поножи и перчатки с исходными именами Oblivion
(`Mesh_0001`) не отображались. Вывод переименовывает формы (`mesh_convert::skin::name_shapes`).

**Место форм в дереве.** Во всех 168 скиннинговых частях тела `Morrowind.bsa` (2026-09-25)
скиннинговая форма лежит **внутри** `Bip01`: прямо под ним (26 файлов и рубашки) или под узлом
слота внутри него (`Chest`/`chest` — 92, `Left Hand`/`Right Hand` под `UpperArm` — перчатки,
`Bip01 L Thigh` — сапоги). Корень файла — `Bip01` (большинство) или узел с именем файла, над
`Bip01`. Ни одной формы рядом с `Bip01`. Флаги у ванили ненулевые: узлы `0xc` (реже `0xa`),
формы `0x4` (реже `0x2`); у нас `0`. Вывод до 2026-09-25 клал формы соседями `Bip01` под
`Scene Root` — с ним кирасы и перчатки с верными именами `Tri Chest`/`Tri … Hand` в игре не
отображались. Теперь формы — дети `Bip01`. **Не проверено** в игре, что этого достаточно; если
нет — следующий кандидат флаги.

## Броня и одежда: слоты и части тела

Номера `INDX` у `ARMO`/`CLOT` (слоты): 0 голова, 1 волосы, 2 шея, 3 кираса/грудь, 4 пах, 5 юбка,
6/7 правая/левая кисть, 8/9 правое/левое запястье, 10 щит, 11/12 предплечья, 13/14 плечи, 15/16
ступни, 17/18 лодыжки, 19/20 колени, 21/22 бёдра, 23/24 наплечники, 25 оружие, 26 хвост.
Части `MP_*` у `BODY`: 0 голова, 1 волосы, 2 шея, 3 грудь, 4 пах, 5 кисть, 6 запястье,
7 предплечье, 8 плечо, 9 ступня, 10 лодыжка, 11 колено, 12 бедро, 13 ключица, 14 хвост.

**Пустой `INDX` прячет часть тела.** Слот без `BNAM`/`CNAM` ничего не рисует, но тело под ним
не показывается. Ваниль так делает сама (2026-09-25): в `Morrowind.esm` 153 пустых `INDX` из
1164 — перчатки прячут запястья (8/9), сапоги и мантии — лодыжки (17/18); в `Tribunal.esm` ещё
и пах (4). Oblivion же не рисует тело под занятым слотом вообще (верх — торс и руки до запястий,
низ — пах и ноги до щиколоток), и его меш несёт всё видимое сам. Поэтому вещь получает пустые
части на все слоты Morrowind, которые закрывает её набор слотов Oblivion
(`transform::worn::covered_slots`); без них руки и ноги тела торчали сквозь кирасу Black Knife
(игра, 2026-09-25). Что другая броня (поножи, наручи) при этом не пропадает — **не проверено**
в игре (у OpenMW при равном приоритете слот берёт вещь, обработанная позже; кираса — раньше
поножей, сапог и перчаток).

**Кожа Oblivion в мешах вещей** (2026-09-30, решение владельца). Oblivion кладёт в меш брони и
одежды куски тела с текстурой имперской кожи (`textures\characters\imperial\{male,female}\
{upperbody,leg,hand,foot}….dds`) и на лету подменяет её кожей расы носящего. Morrowind так не
умеет: у тёмной соблазнительницы живот выходил человеческим, у аргонианки руки (игра). Теперь
`mesh_convert::skin::drop_skin` выбрасывает треугольники кожи, чья главная кость лежит вне слота
самой части (`transform::worn::bone_slots`: `Spine*`/`Clavicle` — грудь, `Pelvis` — пах,
`Thigh` — бедро, `Calf` — колено и лодыжка, `Foot` — ступня, `UpperArm`/`Forearm` — плечо и
предплечье, `Hand`/`Finger` — кисть и запястье), и конвейер снимает с вещи пустые слоты там, где
кожа ушла: видно ванильное тело нужной расы. На собственном слоте кожа **остаётся имперской**:
движок прячет тело под ним, и без куска была бы дыра (живот у доспеха соблазнительницы). Опустевшая
форма убирается из меша совсем: движок ищет части `Tri <узел> 0`, `1`, … по номерам с нуля и без
нулевой не находит ни одной («Not able to find Chest part», игра, 2026-09-30; у ванильной кирасы
`Tri Chest 0`, `1`, `2` подряд). `SEWorld` — снято 283 пустых слота. Нет ли щелей на стыках тела
Morrowind с мешем Oblivion — **не проверено** в игре.

**Материал: ambient** (2026-09-30, решение владельца). Morrowind освещает материал рассеянным
светом × ambient плюс прямым × diffuse, и с ambient 0 всё, что отвёрнуто от ламп, выходит чисто
чёрным (рукава рубашек в домах). Нулевой ambient становится diffuse (`mesh_convert::material`;
в `SEWorld` было 956 таких форм). У голов и причёсок ambient = diffuse (`head::tint_properties`):
у ванильных голов он 1.0, у голов Oblivion 0.588, 0.25 или 0, и в тени лицо было темнее шеи.
Осталось 99 форм с ambient 0 — у них и diffuse 0 (эффекты, светятся emissive).

**Текстура причёски — из `HAIR`** (2026-09-30). Oblivion берёт текстуру причёски из `ICON`
записи `HAIR`, а не из её NIF: у гривы текстуры из NIF (`characters\hair\grey_mane.dds`) в его
архивах нет вовсе, и игра писала «tex not found». Конвертер ставит причёске текстуру `ICON`
(`back2mw::faces`), без `ICON` — текстуру NIF.

**Не больше 7 частей на вещь** (2026-09-30). Во всех трёх ванильных мастерах ни у одной
`ARMO`/`CLOT` нет больше 7 `INDX`. `SEWorld.esp` с 58 вещами на 9…19 частей (пустые слоты полного
доспеха или мантии) ронял ванильный движок при загрузке плагина, и не всегда в одном месте:
`Morrowind.exe+0xEE8B0` или `msvcrt.dll+0x8EE37`, а иногда игра загружалась. Деление плагина по
типам записей показало: `BODY` отдельно грузится, `ARMO`+`BODY` и `CLOT`+`BODY` падают. Похоже на
запись за конец массива из 7 частей, но размер массива в самом движке **не проверен**. Поэтому
пустые слоты отбираются по заметности (`transform::worn::HIDE_PRIORITY`, решение владельца):
торс, пах, бёдра, колени, плечи, предплечья, лодыжки, ступни, кисти, запястья. Пара правый/левый
берётся целиком или не берётся. У кирасы «верх + низ + ступни» остаются грудь, пах, бёдра и
колени, у мантии тоже. Не торчит ли тело сквозь меш на плечах и голенях — **не проверено** в игре.

**Иконки** ванили — 32×32 (948 из 951 иконки вещей в `Morrowind.bsa`, DXT3/DXT1), движок рисует
их в собственном размере. Иконки Oblivion 64×64 в инвентаре вдвое крупнее (игра, 2026-09-25),
поэтому уменьшаются до 32×32 (`mesh_convert::icons`).

Как это делает ваниль (`Morrowind.esm` + DLC, 2026-09-24):

| Тип | Всего | Типичные слоты |
|---|---|---|
| шлем | 72 | `[0]` голова — 43, `[1]` волосы — 29 |
| кираса | 51 | `[3]` — 50 |
| поножи | 25 | `[4, 22, 21, 20, 19]` |
| сапоги | 33 | `[16, 18, 15, 17]` |
| перчатки | 24 + 25 | левая `[7, 9]`, правая `[6, 8]` — **отдельные вещи** |
| щит | 60 | `[10]`, `BODY` с частью **`Wrist`** |

Поле расы у `BODY` брони в ванили заполнено всегда (566 — «Argonian», значение CS по умолчанию).
Мы пишем пустое; **⛔ CS:** примет ли он пустую расу у брони — не проверено.
